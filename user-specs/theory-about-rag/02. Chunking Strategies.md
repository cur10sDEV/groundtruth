### Core Interview Question

> _"You have a 100-page document. How would you chunk it for a Retrieval-Augmented Generation (RAG) system?"_ 

### Selecting Token Lengths & Trade-offs

- **Small Chunks (~100 tokens):** High-quality, precise embeddings, but loses broader context
- **Large Chunks (~2,000 tokens):** Captures complete information, but causes **context dilution**, degrading embedding precision
- **Document-Specific Guidelines:**
    - **Legal Documents:** Require longer chunks (e.g., 800+ tokens) due to cross-references and complex arguments
	- **FAQ Documents:** Require shorter chunks (e.g., ~100–200 tokens) since each Q&A is self-contained
    - **Research Papers:** Require medium chunks (e.g., ~400 tokens)


# Structure-Aware / Recursive Chunking (Intermediate Approach)

- **Mechanism:** Parses structural markers (HTML headers like `<h1>`/`<h2>`, Markdown `#`/`##`, sections, or paragraphs) to define chunk boundaries 
- **Hierarchy:**      
    1. Split by main sections (`H1`)
    2. If the section is too large (> token threshold), recursively split into sub-sections (`H2`/`H3`)
	3. Further split into paragraphs $\rightarrow$ sentences $\rightarrow$ tokens if necessary 
- **Advantages:** Chunks are semantically coherent, yielding clearer embeddings and higher retrieval accuracy


# Parent-Child & Sentence-Window Retrieval

- **Core Concept:** Decouple the text used for **embedding/retrieval** from the text passed to the **LLM for generation**
- **Architecture:**
    - **Child Chunks:** Small chunks (~100–200 tokens) optimized for precise vector matching
    - **Parent Chunks:** Larger surrounding context blocks mapped to one or more child chunks

### Step-by-Step Mechanical Workflow

#### 1. Dual-Layer Ingestion (Splitting & Mapping)

- **Parent Chunks:** The document is split into larger sections (e.g., 1,000–2,000 tokens or full logical sections/paragraphs). These contain comprehensive context.
- **Child Chunks:** Each Parent chunk is further split into smaller units (e.g., 100–200 tokens or single sentences).
- **ID Linking:** Each Child chunk is assigned a metadata attribute containing its parent's unique identifier (`parent_id`).

#### 2. Storage Setup (Vector Store vs. Document Store)

- **Vector DB (Child Storage):** Only the **Child chunks** are vector-embedded and indexed. This keeps the vector index compact and high-precision.
- **In-Memory / Key-Value Store (Parent Storage):** The full **Parent chunks** are stored in a key-value store (e.g., Redis, Mongo, or an in-memory `DocStore`) using their `parent_id` as the lookup key.

#### 3. Query & Retrieval Execution

1. **Vector Search:** The query vector is compared _only_ against the **Child embeddings** in the Vector DB to find the top $k$ closest matches.
2. **Metadata Lookup:** The retriever extracts the `parent_id` values attached to those winning Child chunks.
3. **Parent Fetching:** The system uses those keys to fetch the larger **Parent chunks** from the key-value store.
4. **Deduplication:** If multiple retrieved Child chunks belong to the same parent, the system *deduplicates* the `parent_id` list so the LLM doesn't receive redundant context.
5. **Generation:** The full Parent context is passed into the prompt payload for the LLM.

### Key Variations in Implementation

- **Full Parent Retrieval:** The exact parent chunk (e.g., a 1,500-token section) is fetched upon hitting any child node within it.
- **Sentence-Window Retrieval:** A special form of parent-child relationship where the child is a single sentence. When retrieved, the engine dynamically *extracts a "window" of $x$ sentences surrounding that single sentence* (e.g., 3 sentences before and 3 sentences after).
- **When to Use:** Long documents with hierarchical structures where deep context is necessary for generation, but small units are needed for retrieval (e.g., LlamaIndex `SentenceWindowNodeParser`)


# Advanced Chunking Strategies

### A. Semantic Chunking via Sentence Embeddings

1. Break text into individual sentences
2. Generate embeddings for consecutive sentences
3. Calculate Cosine Similarity between adjacent sentence pairs
4. If similarity is above a threshold, group them into the same chunk. When similarity drops significantly, split and start a new chunk
   
- **Advantage:** Dynamically detects topic shifts without relying on structural markers   
- **Limitation:** Computationally expensive and requires hyperparameter tuning for threshold cutoffs

### B. Proposition-Based Chunking

- **Mechanism:** Uses an LLM to decompose complex text into atomic, self-contained factual statements ("propositions")
- **Advantage:** Extremely high retrieval precision and token-efficient generation
- **Limitation:** Very expensive and slow due to LLM preprocessing
- **Best Used For:** High-stakes, high-accuracy domains such as legal, financial, or medical document processing


# RAG Evaluation Metrics & Chunk Tuning

To systematically test and select the optimal chunking strategy, build a benchmark evaluation set (50–100 question-answer pairs with known source context) and evaluate using the following metrics:

| **Metric**                     | **Definition**                                                                  | **Purpose**                                             |
| ------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------- |
| **Retrieval Recall**           | Fraction of relevant source chunks successfully retrieved.                      | Measures if the retriever missed necessary information. |
| **Mean Reciprocal Rank (MRR)** | Evaluates how high up in the search results the first relevant chunk appears.   | Measures ranking quality of vector search.              |
| **Context Precision**          | Fraction of retrieved chunks that were actually useful vs. noise.               | Measures noise reduction in context window.             |
| **Answer Faithfulness**        | Verifies if the generated answer is strictly grounded in the retrieved context. | Identifies and quantifies **LLM Hallucinations**.       |
| **Answer Relevance**           | Assesses whether the LLM output directly answers the user's prompt.             | Ensures task fulfillment.                               |


# Enriching Chunks with Metadata

- **Why Metadata Matters:** Embeddings lack specific categorical metadata (e.g., document name, page number, section, publication year)
- **Benefits:**
    - **Filtering:** Enables structured pre-filtering (e.g., filter by `year=2025` or `chapter=3`) before semantic search
    - **Traceability & Speed:** Reduces search space, speeding up responses and improving answer precision
