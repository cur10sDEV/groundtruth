# HyDE (Hypethetical Document Embedding)

Instead of searching the vector store for the user query, **HyDE** first generates an answer from the LLM's own internal knowledge and stores it as a document. Then, it uses this document's embeddings to search the vector store for relevant chunks.

> You can use HyDE as a fallback if retrieved context is not upto the mark or not present for the user query - It performs the **query expansion (detailed paraphrasing)**


# Caching

### Caching layers (distinct mechanisms)

- **Exact-match** - hash identical queries, cheap but low recall
- **Semantic** - embed + similarity threshold - every query will be checked against cache in a multi turn setup - so context can be ignored here - **works best for single turn queries**
- **Retrieval cache** - cache retrieved chunks separately from final response alongwith metadata (can be used for citations)
- **Prefix/KV cache** - caches compute for identical leading tokens — this is the critical one for multi-turn threads

### Core conflict discovered

- KV caching only hits on byte-identical prefixes
- Rewriting/replacing a summary mid-thread breaks the **cached prefix** from that point onward → forces reprocessing, defeating the savings
- Resolution: default to **append-only growing history** (cache-friendly); only compact when forced

## Semantic Caching

- When using semantic caching you dont simply store the user query as is - You can paraphrase and normalize it using LLM so that two semantically similar queries can query the same results from the cache with higher similarity score

- You simply cannot trust the user query / input - they might have added redundant or not so useful info to the query - that is why this **normalization** is necessary. However it depends totally on the use case and the query patterns - the whole query normalization is **lossy** so there are trade-offs.

- Also caching might not be very helpful in systems where you cannot directly serve the cached results - suppose an enterprise system where RBAC is necessary - and even though we have cached the query - the results might be different depending on the user role or the user might not have enough permissions to see any results whatsoever  (out of scope | 401)

- In addition to paraphrasing, you can acutally extract **Key Entities** - that might have better chance of having higher cache hit rate
	- You can also store generated multiple queries (paraphrased) - to have even higher cache hit

> Naive normalization could be fixing typos, grammar, etc and we use cheaper model for this purpose.

## Hashing and normalization

- Normalize the incoming query (lowercase it, strip whitespace) and generate a hash from it (MD5 or SHA-256) to use as the cache key.
- Works where the query is static - FAQ style, pre-generated queries, no user input, etc.

> General rule is to only *cache LLM responses* for queries where the answer is stable over the cache duration. Static reference information, definitions, historical facts. Not policy questions, not questions about current state, not anything where the correct answer might change.

## Invalidation

- You should have metadata filters to delete the old chunks associated with a document / user / org when either an update or deletion happens for that document or user or organization.
- **tag** entries with an index **version/generation number** and invalidate (or treat as a cache miss) whenever the index advances past that version
- Always have a TTL
